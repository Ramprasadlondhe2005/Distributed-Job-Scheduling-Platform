## Key Design Decisions

### Primary Keys
All entities use **UUID v4** primary keys generated by PostgreSQL. This ensures:
- No sequential ID enumeration attacks
- Safe for distributed systems where IDs may need to be known before DB commit

### Foreign Keys & Cascading
| Parent | Child | On Delete |
|---|---|---|
| Organization | User | Restrict (users must be removed manually) |
| Organization | Project | Cascade |
| Project | Queue | Cascade |
| Queue | Job | Cascade |
| Job | JobSchedule | Cascade |
| Job | Execution | Cascade |
| Execution | ExecutionAttempt | Cascade |
| Execution | DeadLetterMessage | SetNull (keep DLQ record even if execution gone) |
| Worker | Execution | SetNull (execution survives worker removal) |

### Indexes
| Table | Index | Reason |
|---|---|---|
| executions | `(status, scheduledFor)` | Scheduler queries due executions by status + time |
| executions | `nextAttemptAt` | Retry polling queries |
| executions | `lockedByWorkerId` | Worker lookup for heartbeat updates |
| job_schedules | `nextRunAt` | Recurring job scheduler polling |
| jobs | `(status, type)` | Filter active/recurring jobs quickly |
| jobs | `runAt` | One-time job scheduler polling |
| audit_events | `createdAt` | Timeline queries |
| audit_events | `(actorType, actorId)` | Filter by actor |
| workers | `(status, lastHeartbeatAt)` | Stalled worker detection |

### Normalization
- Schema is in **3NF** — retry configuration is stored in the `Job` table (not a separate `RetryPolicy` table) for simplicity, as retry is tightly coupled to a specific job's configuration.
- `JobSchedule` is separated from `Job` to keep the `jobs` table lean and only populated for `RECURRING` jobs.
- `ExecutionAttempt` records each individual HTTP attempt separately, enabling full retry history without losing previous attempt data.
